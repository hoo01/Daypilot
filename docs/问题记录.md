## [2026-06-06] Chat 接口延迟过高

### 问题描述

`POST /chat/` 每轮对话耗时 30 秒以上。

### 根本原因

`before_agent_callback` 用 `asyncio.gather` 并行调用三个预加载工具：

```python
ctx, goals, rel, health = await asyncio.gather(
    read_user_context(user_id),
    track_goals(user_id),
    get_relationship_context(user_id),
    analyze_health(user_id),
)
```

但三个工具内部都用了**同步** Gemini SDK 调用：

```python
# 错误：阻塞 event loop，asyncio.gather 无法真正并行
response = client.models.generate_content(...)
```

同步调用会阻塞整个 event loop，导致三个 Gemini 调用实际串行执行。  
加上 coordinator 自身的调用，每轮对话共 4 次串行 Gemini 请求。

### 解决方案

**修复一：同步改异步（`relationship_tools.py`、`goal_tools.py`、`insights_engine.py`）**

```python
# 改为异步调用，asyncio.gather 才能真正并行
response = await client.aio.models.generate_content(...)
```

**修复二：relationship context 加缓存（`relationship_tools.py`）**

upcoming events 在 session 期间不会变，缓存 30 分钟：

```python
_cache: dict[str, tuple[float, dict]] = {}
_CACHE_TTL = 1800

cache_key = f"{user_id}:{date.today().isoformat()}"
now = time.monotonic()
if cache_key in _cache:
    ts, cached = _cache[cache_key]
    if now - ts < _CACHE_TTL:
        return cached
```

**修复三：health pipeline 加缓存（`health_tools.py`）**

health pipeline 使用静态 demo 数据，同一天结果不变，缓存 10 分钟：

```python
_CACHE_TTL = 600
cache_key = f"{user_id}:{target_date}:{scenario}"
```

**修复四：preload 工具改用更快的模型（`config.py`）**

`relationship` 和 `goals` 的任务是简单 JSON 生成，不需要 thinking 模型：

```python
# 改前
relationship_model: str = "gemini-2.5-flash"   # ~15s
goal_model: str = "gemini-2.5-flash"            # ~9s

# 改后
relationship_model: str = "gemini-2.5-flash-lite"  # ~2s（非 thinking）
goal_model: str = "gemini-2.5-flash-lite"
```

> 注意：`gemini-2.0-flash` 和 `gemini-1.5-flash` 已下线，不可用。

### 效果

| | 改前 | 改后（冷启动） | 改后（缓存命中） |
|---|---|---|---|
| relationship | ~15s | ~12s | 0ms |
| goals | ~9s | ~2.5s | 不缓存（goal progress 会变） |
| health | ~5s | ~5s | 0ms |
| **总延迟** | **~30s** | **~15s** | **~5-8s** |

### 注意事项

- `goals` 不缓存：`/schedule/feedback` 会更新 goal progress，缓存会导致 coordinator 读到旧数据，反馈闭环失效
- Demo 前建议先发一条消息热身，之后对话流畅

## [2026-06-08] plan_schedule 相关的四个问题（手动测试发现）

通过在前端手动走一遍 "Plan my day" 流程，发现并修复了四个问题。

### 问题一：`plan_schedule` 本身耗时过长（~36s）

`POST /chat/` 在涉及生成 schedule 时单独耗时 30s+，且与上面 [2026-06-06] 的预加载延迟无关——
拆解后发现瓶颈 100% 集中在 `plan_schedule` 这一次 Gemini 调用：3 个 strategy × ~17 个 task ≈ 52 个结构化
JSON 对象，输出 token 量直接决定耗时，跟 `thinking_budget=0` 无关。

**修复**：`config.py` 把 `planning_model` 从 `gemini-2.5-flash` 换成 `gemini-2.5-flash-lite`。

| | 改前 | 改后 |
|---|---|---|
| `plan_schedule` 单独耗时 | ~36.5s | ~28.6s |
| `/chat/` 端到端（含 schedule 生成） | ~36-52s | ~26.5s |
| 输出质量 | — | 无损（任务标题、calendar_event 时间地点均正确）|

> 模型本身只是次要因素——耗时和输出 task 数量强相关。真正要大幅提速需要从源头减少单次输出量
> （比如先只生成 1 个 strategy，按需再生成另外两个）。

### 问题二：ML class 这类用户提到的事件被错误解析 / 合并成通用任务

种子数据里事件是非结构化自然语言字符串（`"ML class 2PM-4PM at library"`），且 `plan_schedule`
的 docstring 没写明 `calendar_events` 参数的 schema，导致 Gemini 经常把 "2PM-4PM" 解析错，或者把
该事件合并进通用的 study/personal 块。

**修复**（`agents/tools/schedule_tools.py`）：
1. `_normalize_timestamp` 增加对 12 小时制时间格式的支持（`"2PM"`、`"2:00 PM"`、`"2pm"` 等）
2. 给 `plan_schedule` 的 docstring 补充 `calendar_events` 的精确 schema 和示例

### 问题三：生成的任务会和 calendar_event 时间重叠

`_enforce_constraints` 已经有逻辑会清掉跟 **locked blocks** 冲突的生成任务，但漏了对
**calendar events** 做同样处理——实测中出现过 "Personal Time"（1-3PM）和 "ML Class"（2-4PM）
重叠 1 小时的情况。

**修复**（`agents/tools/schedule_tools.py` → `_enforce_constraints`）：比照 locked blocks 的做法，
丢弃任何与 calendar_event 类型任务时间重叠的生成任务：

```python
cal_tasks = [t for t in tasks if t.type == "calendar_event"]
if cal_tasks:
    tasks = [
        t for t in tasks
        if t.type == "calendar_event" or not any(
            _times_overlap(t.start_time, t.end_time, c.start_time, c.end_time)
            for c in cal_tasks
        )
    ]
```

### 问题四：用户不重新提起时，coordinator 不会主动带出"今天已知的事件"

这是最关键的一个——直接影响 demo 脚本里 "He didn't tell it any of this today. DayPilot already
knew." 这条核心叙事。

预加载的 context 里其实已经有 `"ML class 2PM-4PM at library"`（`days_away: 0`，还带着对应的
proactive suggestion），但 coordinator 的 CRITICAL rules 只覆盖了"**用户提到**某个事件时必须传
calendar_event"，没覆盖"DayPilot 自己已经知道、用户没提"的情况。结果用户只说 "please plan my
day"，生成的 schedule 里凭空出现几个时段空白（正好是 ML class 应该在的位置），回复里也完全不提。

**修复**（`agents/coordinator.py` INSTRUCTION）：在 CRITICAL rules 里新增一条，要求 coordinator
主动检查 `<user_context>` 里 `days_away: 0`（今天）的 upcoming events，即使用户没有重新提起，
也要作为 calendar_event 传入。

修复后用 `demo_user` + "please plan my day" 重测：proactive suggestion 正确提到
"Your ML class is today from 2PM-4PM at the library..."，schedule 里也正确出现
"2:00 PM - 4:00 PM: ML class at library (Calendar Event)"，前后自动安排了 commute，无重叠。

### 注意事项

- 以上四处改动均已通过直接调用 `/chat/` API 验证（`demo_user`），无需切前端账号复测——
  它们都是纯后端逻辑，前端只是原样渲染文本，不存在前端特有的风险点
- 前端测试时注意：登录会生成随机 `user_id` 并存入 `localStorage`，新账号在数据库里没有
  `demo_user` 的种子数据（没有 "今天有 ML class" 这条），看不到这些场景属于正常现象，不是 bug

## [2026-06-08] Schedule 策略中出现长时间空档——bug 还是值得保留的特性？

### 现象

手动测试 "Plan my day" 时发现，"Most Productive" 策略里 8:30-9:00 AM "Preparation for ML
Class" 之后直接跳到 1:30 PM "Commute to Library"，中间近 4.5 小时完全没有任务；"Fastest"
策略也有类似但更短的空档（11:30 AM 午饭后到 1:30 PM 通勤之间空 1.5 小时）。这与 prompt 里
"Each strategy must cover the full day from wake-up to sleep" 的规则相悖，且 `_validate_and_fix`
/ `_enforce_constraints`（`agents/tools/schedule_tools.py`）目前都只处理"任务重叠"，没有
"检测全天覆盖空档"的逻辑——这是和 [2026-06-08 问题三]（任务与 calendar_event 重叠，即
"太密"）正好相反的另一面问题。

### 讨论：是 bug 还是值得保留的特性？

最初判断这是模型生成遗漏（bug）。但反向看：对于 MBTI "P 人"（随性 / 灵活型用户）来说，
被排得密密麻麻、每分钟都标注做什么的日程表反而带来压迫感（"两眼一黑"）；适度留白传递的是
"工具服务于人，而非把人当机器调度"的体验。"Most Productive" 里这段空白甚至可以解读成——
系统没有强行把准备时间拉长填满整个上午，而是把自由支配权交还给用户，跟"过度规划"形成
一种巧妙对比。

### 待解决

若想稳定呈现这种"留白"效果，不能依赖模型偶然遗漏——同样的输入下次未必复现，而且空档出现
的位置可能很随机/突兀（比如卡在一天中段、紧贴着 ML class 之前）。要把它变成可控的产品行为，
需要在 `plan_schedule` 的 prompt 里显式引导，例如允许 "Most Productive" 策略保留一段
"flexible / unscheduled time" 区块（有明确标签和合理位置），而不是把它当成需要修复的生成
缺陷消灭掉。这样既能保留对 "P 人" 友好的观感，又不会让 demo 时的空档变成不可控的随机噪声。
